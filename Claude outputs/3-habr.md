## Заголовок

**Один тестировщик, 71 инструмент и два реальных бага, которые я сам у себя нашёл: как я строю Wrench-Branch в одиночку**

## Текст статьи

Полтора года в QA приучают к одной простой мысли: если что-то можно автоматизировать — это стоит автоматизировать, включая собственную рутину. У меня рутина была такая: JSON нужно отформатировать — открываю рандомный сайт с рекламой. Нужен UUID — ещё один сайт. Нужно проверить cron-выражение — третий. Каждый раз новый безымянный домен, и каждый раз мысль "а кому я вообще сейчас скопировал эти данные".

В какой-то момент я решил закрыть это для себя раз и навсегда и сделать один инструмент вместо десяти вкладок. Так появился **Wrench-Branch** — сейчас там 71 живой инструмент в 10 категориях (API, кодирование, форматирование, генераторы, hash, QA, текст, дата/время и т.д.), почти всё считается прямо в браузере, без отправки данных на сервер.

Дальше — не столько питч, сколько рассказ о том, что происходит, когда тестировщик строит продукт соло и потом сам же его тестирует.

### Что внутри

Кроме самих инструментов, там два узла, которые я считаю самыми интересными архитектурно:

**Workbench** — личный дашборд, куда можно закрепить свои часто используемые инструменты, с drag-and-drop сортировкой и несколькими именованными наборами (например, отдельный набор "для API-тестирования" и отдельный "для фронтенда"). На бесплатном тарифе — 1 воркбенч на 6 тулз, на Pro — 5 воркбенчей по 16.

**Daily Challenges** — ежедневные задачки в духе шахматных puzzle с chess.com, только на QA/dev-тематику, со streak-механикой и лидербордом. Идея простая: пять минут в день на разминку скилов, а не очередной курс на 40 часов, который никто не закончит.

Ещё есть несколько AI-инструментов (сгенерировать regex по описанию на человеческом языке, сгенерировать тест-кейсы по API-спеке или user story, объяснить произвольный JSON) — на бесплатном тарифе 3 генерации в день, на Pro безлимит.

Стек: Next.js 14 (App Router), TypeScript, Tailwind, Supabase (auth + Postgres/RLS), Stripe для Pro-подписки ($5/мес), деплой на Vercel.

### Баг №1: тестировщик тестирует свой cron-парсер

У инструмента "Cron Expression Parser" есть фича — показать 5 ближайших запусков по выражению. Реализация внутри — честный перебор по минутам вперёд, с ограничением числа попыток, чтобы не зависнуть, если выражение невалидное.

Лимит стоял в 10 000 попыток — это примерно 6.9 дней вперёд по минутам. На вид с запасом. Но для будничных расписаний вроде `0 9 * * 1-5` (по будням в 9:00) 5-й ближайший запуск может лежать почти в 7 днях от текущего момента — например, если сейчас вечер пятницы после 9 утра, то нужно найти пн-вт-ср-чт-пт следующей недели. Это вплотную к границе лимита, и в CI (GitHub Actions) тест **иногда** падал — находилось только 4 запуска из 5, в зависимости от того, в какой день и час реально выполнялся прогон.

Классический пример бага, который не воспроизводится стабильно локально, потому что зависит от текущей даты/времени выполнения — а не от кода как такового. Нашёл его не руками, а по логам упавшего CI-рана.

Фикс — поднять лимит с запасом:

```ts
// Было: 10000 попыток — впритык для будничных расписаний
// Стало: с большим запасом, перебор по минутам всё равно дешёвый
let attempts = 0;
while (results.length < count && attempts++ < 200000) {
  // ...
}
```

### Баг №2: один компонент, два разных случайных текста

Второй баг интереснее с архитектурной точки зрения. Инструмент "Lorem Ipsum Generator" генерировал текст так:

```tsx
// Было
const output = useMemo(() => {
  return genParagraphs(count); // Math.random() внутри
}, [count, type, lang]);
```

Выглядит невинно, но в Next.js с SSR это генерирует контент дважды: один раз на сервере при рендере страницы, второй раз на клиенте при первой гидратации. `Math.random()` на сервере и `Math.random()` на клиенте — это два разных запуска JS-рантайма, соответственно два разных случайных текста. React тихо "доверяет" клиентскому результату при гидратации, так что пользователь на долю секунды получает рассинхрон: счётчик "N слов / M символов" посчитан по одному тексту, а в textarea уже лежит другой.

В обычном использовании это почти незаметно — глазом не поймать миллисекундный мерцающий пересчёт счётчика. А вот Playwright-тест, который читает textarea и счётчик в разные моменты, ловит это стабильно как несовпадение.

Фикс — вынести генерацию из рендера в эффект, чтобы и сервер, и первый клиентский рендер гарантированно совпадали (оба дают пустую строку, а дальше уже одинаково досчитывают на клиенте):

```tsx
// Стало
const [output, setOutput] = useState("");
useEffect(() => {
  setOutput(genParagraphs(count));
}, [count, type, lang]);
```

Это, в свою очередь, создало третью проблему поменьше — тест мог прочитать textarea на кадр раньше, чем сработает эффект. Решилось ожиданием заполнения в самом тесте (Page Object), а не костылями в компоненте.

Мораль, которую я для себя вынес: `Math.random()` (и `crypto.getRandomValues()`) в теле рендера в связке с SSR — это баг, который почти невозможно поймать глазами, но который надёжно ловит нормальный E2E-тест. Если у вас в кодовой базе есть похожий паттерн — стоит перепроверить.

### Тестирование как часть продукта, а не довесок

Я осознанно решил строить Playwright E2E-сьют параллельно с продуктом, а не после — 30-60 минут по вечерам, чтобы не съедать время у поиска работы (сейчас я в активном джоб-серче). За это время сьют уже нашёл несколько реальных продакшн-багов до того, как они добрались до пользователей: сломанный редирект `/profile` после логаута, гонку при навигации на выходе из аккаунта, тихий дубль email при регистрации, задвоенные записи в реестре инструментов (из-за которых два инструмента реально отдавали 404 в проде). Два бага выше — из той же серии, просто пойманы уже после того, как код побывал в CI.

Как QA-инженеру мне это откровенно доставляет удовольствие — ловить баги в собственном продукте тем же инструментом, которым я ловлю их на работе.

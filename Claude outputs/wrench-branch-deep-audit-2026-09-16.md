# Wrench-Branch — глубокий аудит продукта
Дата: 16 сентября 2026. Метод: статический анализ кодовой базы (`/tmp/wrench-sync`, синхронный клон), без доступа к живой Supabase. Часть находок проверена вручную построчно (отмечено «проверено лично»), остальное — из четырёх параллельных разведок по IA/SEO, экосистеме инструментов, росту/монетизации и техническому здоровью.

Всего у продукта: 82 реализованных инструмента, система daily challenges со streaks и публичным лидербордом, workbench, interview-тренажёр, playground, salary-страница, mock-api, webhook-inspector, daily digest, публичные профили с бейджами, Pro-план $5/мес. Это уже очень много для соло-проекта — большинство находок ниже про полировку и заделанные трещины, а не про отсутствие фундамента.

## 1. Безопасность — критично

### 1.1 Таблица `tool_usage_events` без RLS
Проверено лично: `supabase/schema.sql` включает `enable row level security` для 7 таблиц (`profiles`, `subscriptions`, `teams`, `team_members`, `saved_snippets`, `api_keys`, `ai_credit_ledger`) — строки 16, 40, 64, 65, 111, 129, 149. Для `tool_usage_events` (создана строкой 81) такой строки нет, при этом политики `"Users can insert own usage events"` и `"Users can view own usage events"` (строки 187, 190) для неё определены.

В Postgres/Supabase политики без включённого RLS **не действуют** — таблица открыта по умолчанию для ролей с грантами (`anon`/`authenticated`). Практически это значит: любой может прочитать, кто каким инструментом когда пользовался (по `user_id`), и вставить произвольные строки с чужим `user_id`, искажая аналитику "Popular Tools".

**Фикс:** одна строка миграции — `alter table tool_usage_events enable row level security;`. Могу подготовить файл миграции при следующем шаге.

### 1.2 XSS в Markdown-инструментах
Проверено лично: `components/tools/MarkdownPreviewTool.tsx:70` и `components/tools/MarkdownToHtmlTool.tsx:123` рендерят `dangerouslySetInnerHTML={{ __html: html }}`, где `html` — результат `marked()` прямо из пользовательского textarea, без какой-либо санитизации. В `package.json` и в обоих файлах DOMPurify не подключён вообще.

Показательно, что проект знает про эту проблему: `lib/interview/questions.ts` в собственном банке интервью-вопросов объясняет, что `dangerouslySetInnerHTML` требует DOMPurify — но к своим двум инструментам это знание не применено. Ввод вроде `<img src=x onerror=alert(1)>` в markdown-режиме отрендерится как есть.Self-XSS сам по себе не критичен (жертва — сам вводящий), но если результат когда-либо будет расшариваться (например, через workbench-сниппеты или публичную ссылку) — вектор становится реальным.

**Фикс:** `npm install dompurify` (+ `@types/dompurify`), обернуть `html` в `DOMPurify.sanitize()` перед рендером в обоих файлах.

## 2. Конверсия — критичный баг в самом чувствительном месте воронки

Проверено лично, по цепочке: `app/[locale]/challenges/page.tsx` приглашает пробовать задачи без аккаунта. Но `app/api/challenges/submit/route.ts:97` требует авторизацию и возвращает `401 { error: "Authentication required" }` для гостя. `components/challenges/ChallengeArena.tsx:handleSubmit` (строка 137) кладёт этот ответ в `setResult(data)` без проверки `res.ok`, а рендер результата (строка 274) красит блок в красный и показывает «Не совсем…», если `result.is_correct` не `true` — а у ответа с ошибкой авторизации `is_correct` просто `undefined`.

**Итог:** гость, который честно и правильно решил первую задачу сайта, видит сообщение о провале вместо приглашения зарегистрироваться. Это первое реальное взаимодействие с продуктом для нового посетителя — и оно врёт ему в лицо. Учитывая, что ты используешь продукт как демо для собеседований, это ровно то, что может увидеть рекрутер/интервьюер при первом клике.

**Фикс:** на 401 показывать отдельный UI-блок («Похоже, ответ верный! Зарегистрируйся, чтобы сохранить прогресс и продолжить streak») вместо ветки `is_correct === false`, либо на сервере разрешить анонимную безопасную проверку ответа (без записи в БД) и возвращать реальный `is_correct`.

## 3. RU-локализация — системная проблема, не единичный баг

Найденный ранее баг в `HashGeneratorTool.tsx` оказался не единственным — это симптом более широкого паттерна: инструменты локализуются вручную и по отдельности, без единого источника истины, поэтому часть строк неизбежно проскакивает.

- **`components/tools/UrlEncodeDecodeTool.tsx:39`** — лейбл режима encode жёстко на английском (`"Encoded"`), хотя соседний лейбл на строке 34 для того же режима корректно ветвится через `isRu`.
- **`components/tools/JsonToTypescriptTool.tsx:85`** — сообщение об ошибке парсинга падает в `"Invalid JSON"` без RU-ветки, хотя остальной компонент локализован.
- **Системно, ~15 файлов** (`JsonFormatterTool`, `JsonMinifyTool`, `JsonSortTool`, `JsonValidatorTool`, `JsonEscapeTool`, `JsonMutatorTool`, `HtmlEncodeDecodeTool`, `RegexTesterTool`, `SqlFormatterTool`, `YamlFormatterTool`, `EncodingTools`, `JwtGeneratorTool`, `LiveLocatorTesterTool`, `ScreenshotDiffCheckerTool`, `XpathGeneratorTool`) — сообщения об ошибках ввода никогда не локализуются, даже когда остальной UI — на русском.
- **RU-оверлей не подключён в двух местах**, где должен быть: `app/[locale]/profile/page.tsx:664,666` (карточки сохранённых инструментов) и `components/ToolMapClient.tsx:333,339` (карта инструментов) — рендерят `tool.name`/`shortDescription` напрямую из английского реестра, минуя `localizeTool()`, хотя этот хелпер уже есть и используется в других местах именно для этого.
- **Разнобой в паттерне детекта RU:** большинство файлов сравнивают `dict.common.copy === "Скопировать"` (хрупко — зависит от конкретной строки словаря), 4 файла используют куда более надёжный `locale === "ru"`. Стоит унифицировать на второй вариант — тогда класс багов вроде HashGenerator станет структурно невозможен.

**Рекомендация по приоритету:** не чинить все 15+ файлов построчно вручную — это тот случай, где стоит один раз завести общий helper (`useIsRu()` на основе `locale`, а не строкового сравнения) и системно на него перевести компоненты, вместо повторения точечных патчей.

## 4. IA, навигация, SEO

- **`/map` и `/docs` — страницы-сироты.** У обеих есть `generateMetadata`, но ни одна не залинкована нигде в UI (ни шапка, ни футер, ни поиск, ни `sitemap.ts` для `/map`). Дойти до них можно только зная прямой URL.
- **`app/sitemap.ts` не покрывает ~14 реально существующих и залинкованных разделов**: `/challenges`, `/challenges/[role]`, `/workbench`, `/workbench/gallery`, `/trainer`, `/interview`, `/playground`, `/salary`, `/mock-api`, `/webhook-inspector`, `/digest`, `/people`, `/pro`, `/map`. Это самостоятельные, ценные для SEO страницы, которых Google просто не видит через сайтмап.
- **`<html lang>` не рендерится на сервере.** `app/layout.tsx:60` — без `lang`, атрибут выставляется только на клиенте через `LangSetter.tsx`. Первый HTML, который видит краулер или screen-reader до гидратации — без языка. Это и WCAG 3.1.1, и ослабленный языковой сигнал для EN/RU SEO.
- **`/workbench` — флагманская фича с бейджем "New" — без `generateMetadata` вообще**, наследует дефолтный title/description главной страницы.
- **Дропдаун "Learn" смешивает разнородное:** обучающий контент (Challenges, Interview, Trainer, Knowledge) свалены в одну кучу с самостоятельными dev-утилитами (Mock API, Webhook Inspector, Digest), которые логичнее держать рядом с Tools/Categories. Из-за этого добрались до 10 пунктов в одном дропдауне — то самое раздувание, которое, судя по всему, когда-то уже пытались избежать в верхнем уровне шапки.
- **Крупные фичи не перелинкованы друг с другом.** У самих инструментов и категорий cross-linking сделан хорошо (`ToolLayout.tsx` — "Related tools", `categories/[category]/page.tsx` — "Related Categories"), но `trainer`, `playground`, `mock-api`, `webhook-inspector`, `digest`, `salary` — тупиковые страницы, никуда не ведущие, кроме шапки.
- Из положительного: `lib/seo.ts` корректно генерирует canonical + hreflang en/ru для локализованных пар (не хватает только `x-default`); JSON-LD есть у тулов/статей/challenges, но не у крупных фич; транзакционные страницы (`/auth/*`, `/profile`, `/pro/success`) не закрыты `noindex`, хотя технически не должны индексироваться.

## 5. Экосистема инструментов — контент и покрытие

- **Из 82 реализованных инструментов только ~20 имеют `howToSteps` и ~22 — `faqs`** в `lib/tools-registry.ts` (при том что `whyItMatters` заполнен почти у всех — 83 записи). То есть у ~60 живых инструментов нет ни пошаговой инструкции, ни FAQ — это и минус для SEO (нет FAQ-схемы для сниппетов в поиске), и ощущение недоделанности для пользователя, который случайно зайдёт на такую страницу.
- **Категория `data` тоньше, чем обещает собственное описание.** В реестре у неё подпись `"Generate fake test data, convert formats, work with CSV"`, но CSV-инструментов (CSV↔JSON, CSV viewer) в продукте нет вообще.
- **Чего не хватает из типового QA/dev-набора:** конвертер часовых поясов (есть только timestamp/date-difference/age-calculator, но не timezone converter), OpenAPI/Swagger-валидатор, парсер User-Agent, IP/CIDR-калькулятор, curl→Postman/Insomnia-коллекция (есть только curl→код), GraphQL query builder/форматтер.
- **UI-паттерны разнородны:** общая обёртка `ToolShell` используется лишь в 16 из 78 файлов компонентов, `CopyButton` — тоже далеко не везде. Показательно: `JsonFormatterTool` использует оба, а его прямой сосед `JsonValidatorTool` — ни одного, с самодельной кнопкой копирования. Итого 20 файлов вообще без общих компонентов — у каждого свой стиль отступов/кнопок. Для пользователя это ощущается как «разные инструменты делали разные люди», даже если это не так.
- Мёртвый код: `components/CategoryCard.tsx` импортирует `allTools`, но нигде в проекте не используется.

## 6. Рост и монетизация

Сильные стороны, которые уже есть и хорошо сделаны: `OnboardingBanner` с чек-листом для нового пользователя (решает проблему "пустого первого экрана"), детерминированный расчёт streak без крона, публичный лидерборд через дайджест, полноценные публичные профили с Wrench Score, бейджами и вставляемым SVG-бейджем для README (`/api/badge/[username]`) — это уже готовый слой доверия, который отлично ложится в твою цель использовать продукт как портфолио.

Пробелы:

- **Соц-proof на сайте почти отсутствует** — нет "N пользователей решили", нет отзывов, нет счётчиков на лендинге, хотя данные для этого уже есть в таблицах (`challenge_attempts`, `profiles`) и могут считаться статически (build-time/ISR), без крона.
- **На чужом публичном профиле нет CTA зарегистрироваться** — если по профилю из README/LinkedIn зайдёт гость, ему некуда идти дальше.
- **Нет шеринга результата** после решения задачи (кнопка "поделиться streak/результатом" в X/LinkedIn) — бесплатный канал роста, чисто клиентская реализация, без бэкенда.
- **Нет предупреждения о риске потери streak** — можно посчитать детерминированно на клиенте по `last_active` без крона и без AI.
- **Workbench полностью закрыт авторизацией без превью для гостя** — для фичи без чувствительных данных это, вероятно, завышенный барьер входа.
- **Pro-план целиком завязан на AI-лимитах** (`ai_usage`, `3/day` free), что прямо противоречит текущему мораторию на продвижение AI-фич до 1500 пользователей. Ценностное предложение Pro сейчас не растёт вместе с продуктом — стоит заранее продумать non-AI ценность (расширенный архив задач уже заявлен на странице цен, но не проверено, гейтится ли он реально в коде; лимиты Workbench уже в коде, но нигде не продаются как повод для апгрейда).

## 7. Техническое здоровье — что ещё стоит знать

- **Часть компонентов тихо глотает ошибки Supabase-запросов** без error-состояния: `ProfileClient.tsx`, `WrenchScoreBadge.tsx`, `AiUsageBadge.tsx` — `.then()` без `.catch()`. При сбое сети бейджи/список использования тулов просто не появляются, неотличимо от «пользователь ничего не делал» — трудно отлаживать в проде.
- **Accessibility:** два интерактивных `<div onClick>` без `role="button"`/`tabIndex`/`onKeyDown` — переворот флэш-карточки и раскрытие FAQ в `components/interview/InterviewPrepClient.tsx:175,232`. Недоступны с клавиатуры.
- **Бандл раздут статическими импортами.** `ToolRenderer.tsx` импортирует все 82 компонента тулов напрямую, включая тяжёлые библиотеки (`marked`, `js-yaml`, `qrcode`) — любая страница `/tools/[slug]` тянет в чанк код всех инструментов и все тяжёлые зависимости разом, даже если открыт простой UUID-генератор. Перевод хотя бы этих трёх на `next/dynamic` даст заметный выигрыш.
- **~17% инструментов (по грубой прикидке) без e2e-покрытия** — разумно для соло-проекта, но стоит иметь в виду при следующих правках этих тулов.
- **Мусор в репозитории:** файл `tatus` в корне — похоже на случайно сохранённый `git diff` вместо вывода в терминал; `.verify_webhook_sig.py`/`.verify_webhook_sig2.py` — черновые скрипты ручной проверки, не часть приложения. Плюс уже обсуждённая пара `challenges-seed.sql`/`challenges-seed-fixed.sql`. Ничего критичного, но стоит почистить для порядка.
- Из хорошего: `tsconfig.json` со `strict: true`, нет подавленных ESLint-правил, нет `ignoreBuildErrors`/`ignoreDuringBuilds` в `next.config.js`, TODO/FIXME/console.log-мусора в коде практически нет — прод-гигиена в целом на хорошем уровне.

## Как предлагаю двигаться дальше

Список получился большим — предлагаю не пытаться закрыть всё разом. Логичный порядок:

1. Сначала — 3 критичных пункта из раздела 0 (RLS, XSS, баг гостевого submit) — это безопасность и первое впечатление, короткие точечные фиксы.
2. Затем — на твой выбор: либо системный проход по RU-локализации (унификация `isRu`-паттерна + 2 конкретных бага), либо IA/SEO-пачка (sitemap, orphan pages, `lang` атрибут), либо что-то из роста/монетизации.
3. Контент-пробелы (FAQ/howTo у 60 инструментов) и недостающие инструменты (CSV, timezone converter и т.д.) — это отдельный, более объёмный пласт работы, имеет смысл вынести в отдельный раунд.
